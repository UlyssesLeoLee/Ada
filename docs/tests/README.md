## 2. 优先级判定原则

- **P0**：核心数据流/安全隔离/数据丢失/合规——任何 P0 失败必须立即修复，阻塞发版
- **P1**：核心功能正确性/性能指标不达标/多租户次级隔离——需在本迭代修复
- **P2**：非核心交互/UI 体验/可观测性——下个迭代修复
- **P3**：边缘场景/极端配置/文档不准确——按 backlog 处理

## 4. 通用测试环境

- **开发环境**：开发者本地，所有外部依赖（Playwright、PostgreSQL、Redis）以容器/进程内嵌方式运行
- **CI 环境**：每次 PR 触发，依赖 `docker-compose` 拉起完整依赖
- **预生产环境**：用于 ST 的端到端测试，配置与生产一致
- **生产环境**：仅做冒烟测试（不在本测试设计书范围内）

## 5. 自动化策略

| 测试类型 | 自动化目标 | 工具 |
|---|---|---|
| UT | 100% 自动化 | Rust 内置 `#[test]` + `cargo test` |
| IT | 100% 自动化 | `cargo test` + `testcontainers`（DB/Redis 容器化） + WireMock（HTTP mock） |
| ST | ≥ 80% 自动化 | Playwright E2E + `k6`/`wrk` 性能压测 + 自研验收测试脚本 |

## 6. 入口/出口条件

### 6.1 入口条件

| 层级 | 入口条件 |
|---|---|
| UT | 模块设计稿评审通过；接口已冻结 |
| IT | 对应模块 UT 通过；依赖模块的 mock 或真实实例就绪 |
| ST | 所有 IT 通过；预生产环境就绪；测试数据准备完成 |

### 6.2 出口条件

| 层级 | 出口条件 |
|---|---|
| UT | 100% 用例执行；P0/P1 全通过；行覆盖 ≥ 80%、分支覆盖 ≥ 70% |
| IT | 100% 用例执行；P0/P1 全通过；接口契约 100% 覆盖 |
| ST | 100% 用例执行；P0/P1 全通过；非功能指标达标；验收硬指标全部满足 |

## 7. 缺陷管理

- 严重等级：S0（数据丢失/安全）/ S1（核心功能失效）/ S2（非核心失效）/ S3（UI/文案）
- 缺陷生命周期：`新建 → 指派 → 修复 → 验证 → 关闭`
- P0/S0 缺陷必须 24 小时内修复或回滚
- 所有缺陷需关联到具体测试用例 ID（`TC-XXX`）

## 8. 维护约定

- 任何 F-IDs、新增模块、修改的接口契约，需同步更新对应测试设计书
- 测试设计书与设计文档同源：设计变更后，关联测试用例需在 1 个工作日内更新
- 用例状态变更（draft → ready → approved）由 QA 负责人审批
