## 1. はじめに（前言）

### 1.1 背景

企业与个人在日常工作中，数据分散于多个互联网平台（社交媒体、SaaS 工具、内部系统、第三方网站等）。这些平台中相当一部分**不提供公开 API**，或 API 存在功能限制、成本壁垒、审核门槛。现有的 iPaaS／ETL 工具（如 DataSpider、Zapier、n8n 等）大多假设"数据源具备可编程接口"，对无 API 场景的支持薄弱，且部署门槛高、二次开发困难。

同时，现有的自动化编排工具在"数据流转"与"控制逻辑"之间缺乏清晰的架构分层，导致系统随着节点数量增长而难以维护、难以推理、难以局部替换。

### 1.2 目的

本文档旨在明确定义"Ada 无限画布跨平台数据集成系统"（以下简称"本系统"）的业务需求、功能需求与非功能需求，作为需求方与开发方之间达成一致理解的基准文档，并作为后续基本设计书、详细设计书及验收测试的依据。

### 1.3 適用範囲

本文档适用于本系统的：
- 需求评审与合意形成
- 架构设计与技术选型决策
- 开发排期与工作量估算
- 验收测试标准制定

本文档不涉及具体的类/模块级详细设计（属于详细設計書范畴）。

### 1.4 読者対象

产品负责人、架构师、Rust 后端开发工程师、前端开发工程师、QA 测试工程师、运维人员。

## 2. 用語定義

| 用語 | 定義 |
|---|---|
| 无限画布（Infinite Canvas） | 一种无固定边界、支持自由缩放与平移的二维可视化操作界面，节点与连线在其上自由排布，本系统前端形态类似 Miro／Figma。 |
| 节点（Node） | 画布上代表一个独立处理单元的可视化元素，对应仿生模型中的"骨骼"。 |
| 数据流（Data Flow） | 在节点间流转的标准化 JSON 数据包及其传输通道，对应仿生模型中的"血液"。 |
| 控制流（Control Flow） | 决定节点执行时机、条件分支、循环、重试等调度逻辑的通道，对应仿生模型中的"肌肉"。 |
| 编排引擎（Orchestration Engine） | 基于 LangGraph 思想实现的状态机式流程编排核心，对应仿生模型中的"神经系统"。 |
| 采集适配器（Acquisition Adapter） | 面向目标平台的接入插件单元，采用"API 连接器优先，无 API 场景回退 Playwright 浏览器自动化采集"的双模式策略，统一转换为标准化 JSON。 |
| 连接器目录（Connector Catalog） | 本系统预置及可扩展的目标平台适配器清单，涵盖 IM/协作、项目管理、CRM、生产制造等类别，详见 3.3 节。 |
| 标准化 JSON（Normalized JSON / NJSON） | 本系统内部统一的数据交换 schema，所有平台数据在进入画布前必须转换为该格式。 |
| Runtime | 基于 Rust 编写的本系统核心执行引擎，负责节点调度、数据流转、资源隔离与免安装分发。 |
| 免安装（Zero-Install） | 用户无需经过传统安装程序（无需管理员权限写入系统目录、无需依赖预装运行库）即可获取并运行本系统。 |
| 无 API 场景（No-API Scenario） | 目标平台未开放官方数据接口，只能通过浏览器可见的 DOM／渲染结果获取信息的场景。 |

## 3. 対象業務・利用者

### 3.1 想定利用者

- **主要用户**：需要将多个无 API 或弱 API 平台的数据进行整合、清洗、路由、二次分发的业务人员、运营人员、数据工程师。
- **次要用户**：需要编写自定义采集适配器或自定义节点的开发者（插件生态贡献者）。

### 3.2 業務シナリオ（用例）

| No. | シナリオ | 説明 |
|---|---|---|
| U-01 | 跨平台内容同步 | 从平台 A（无 API）抓取内容，转换后自动发布至平台 B、C。 |
| U-02 | 多源数据聚合看板 | 定时从多个平台抓取数据，标准化后聚合写入本地数据库或表格。 |
| U-03 | 事件触发式自动化 | 平台 A 出现特定内容变化时，触发条件分支，联动执行下游操作。 |
| U-04 | 数据清洗与人工复核 | 数据流经清洗节点后，进入"人工审核"节点等待人工在画布上确认后再继续流转。 |
| U-05 | 可视化调试与追溯 | 用户在画布上查看每个节点的输入/输出快照，定位数据异常来源。 |
| U-06 | IM 消息双向联动 | 将企业微信/飞书/Slack/Teams/Telegram/WhatsApp/LINE/邮件等渠道的消息统一标准化，实现跨 IM 转发、聚合告警、机器人回复。 |
| U-07 | 项目管理数据同步 | 打通 Jira、Miro、SyncSketch 等平台，实现工单/看板/评审素材的状态同步与自动流转。 |
| U-08 | 企业系统数据集成 | 对接通用 CRM、MES、ERP 等企业内部系统，实现订单、工单、物料、客户数据的跨系统搬运与转换。 |

### 3.3 目标平台清单（连接器目录，Connector Catalog）

本系统的适配范围**不限于无 API 平台**，而是覆盖"有官方 API"到"完全无 API 仅能浏览器可见"的**全谱系**目标系统，采集适配器统一采用"**API 连接器优先、无 API 时自动回退 Playwright 采集**"的双模式策略。初期连接器目录规划如下（后续可通过插件市场持续扩展，不构成穷尽清单）：

| 类别 | 代表性平台/系统 | 典型接入方式 |
|---|---|---|
| 邮件 | Email（IMAP/SMTP/Exchange/Gmail 等） | 优先标准协议（IMAP/SMTP/Graph API），协议不可用时回退网页版采集 |
| IM／协作通讯 | 飞书（Lark）、企业微信、WeChat、LINE、WhatsApp、Telegram、Slack、Microsoft Teams | 优先官方开放平台 API/Webhook/Bot 接口，未开放能力（如个人号无 API 场景）回退 Playwright 采集网页版/客户端内嵌页面 |
| 项目管理／协作设计 | Jira、Miro、SyncSketch 及同类看板/白板/评审工具 | 优先官方 REST API，缺失能力项回退页面采集 |
| CRM | 高度可自定义的通用 CRM（含无公开 API 的私有部署/小众 SaaS CRM） | 提供"通用 CRM 适配器"框架：可视化配置字段映射、自定义 API 端点，或在无 API 时基于页面点选配置采集规则 |
| 生产制造／企业系统 | MES（制造执行系统）、ERP（企业资源计划）等 | 优先标准企业集成方式（REST/SOAP/数据库直连/文件交换），无标准接口的私有化系统回退页面采集或数据库/文件适配器 |
| 其他小众/长尾平台 | 用户自定义的任意 Web 平台 | 通过 F-02 可视化点选与 F-07 插件 SDK，用户可自行扩展任意目标平台的连接器 |

> 说明：连接器目录为**开放式、持续演进**的清单，本文档所列仅为首期规划范围，不作为功能边界的排他性约束；新增平台连接器的成本应被架构设计（F-02/F-07）保证足够低，以支撑"足够底层、足够智能、便于调整"的产品目标。

## 4. システム概要

### 4.1 系统定位

本系统是一套**基于 Rust runtime 的网页版无限画布式通用数据集成与自动化编排工具**，定位为"**类 DataSpider 的下一代万能适配器（Universal Adapter）**"，核心能力包括：

1. 以"**API 连接器优先、无 API 场景自动回退 Playwright 浏览器自动化**"的双模式采集策略，打通邮件、飞书/企业微信/WeChat/LINE/WhatsApp/Telegram/Slack/Teams 等 IM 与协作工具，Jira/Miro/SyncSketch 等项目管理与协作设计平台，高度可自定义的通用 CRM，以及 MES／ERP 等企业生产经营系统，覆盖"有 API"到"完全无 API"的全谱系目标系统（详见 3.3 节连接器目录）；
2. 将提取结果转换为**统一标准化 JSON**；
3. 用户通过**类 Miro 的无限画布网页前端**，以拖拽节点、连线的方式配置数据流转与业务逻辑；
4. Runtime 依据画布配置，驱动数据在节点间**依据数据流与控制流双通道**流转执行；
5. 整个系统**免安装**，前端为可直接访问的网页，后端 Runtime 以单一可执行文件或容器方式分发。

### 4.2 与既存工具的差异化定位

| 比较项 | 传统 iPaaS（如 DataSpider） | 本系统 |
|---|---|---|
| 数据源前提 | 主要依赖已开放的 API/协议连接器，遇到无 API 平台即失效 | API 与无 API 场景通吃：有 API 优先走 API 连接器，无 API 时自动回退浏览器自动化直接抓取渲染层数据 |
| 部署方式 | 通常需要服务器安装与授权 | 免安装、前端网页化、Runtime 单文件分发 |
| 编排模型 | 流程图式，控制与数据耦合 | 数据流与控制流分层解耦（仿生架构） |
| 扩展方式 | 厂商预置连接器为主 | 采集适配器/节点插件化，用户可自定义，长尾/小众平台可自行接入 |
| 覆盖广度 | 以企业系统/数据库为主 | 企业系统（ERP/MES/CRM/Jira 等）与 IM/协作工具（飞书/Slack/WhatsApp 等）并重，一套画布统一编排 |

## 5. アーキテクチャ設計思想（生体仿生モデル）

为使系统在节点数量与业务复杂度增长时仍保持**可推理性**与**可维护性**，本系统采用生物仿生学分层架构，将系统职责映射为生物体的四层结构：

| 生体類比 | 対応するシステム要素 | 職責 |
|---|---|---|
| **骨骼（骨格）** | 节点（Node） | 提供结构性支撑，定义"是什么"——即每个处理单元的静态能力（输入/输出 schema、参数配置、执行逻辑）。骨骼本身不主动运动，仅被驱动。 |
| **血液（データフロー）** | 数据流（Data Flow） | 不受"神经"（编排引擎）的直接强控制，仅依据既定的流转路径（血管，即连线）持续、自主地在节点间搬运标准化 JSON 数据包，类似循环系统的自主调节（自律神经支配之外的物理循环特性）。 |
| **神经系统（LangGraph）** | 编排引擎（Orchestration Engine） | 感知状态、做出决策：条件判断、状态迁移、循环/中断、异常捕获与重试策略。基于 LangGraph 的状态图（StateGraph）模型实现，是系统的"决策中枢"。 |
| **肌肉（制御フロー）** | 控制流（Control Flow） | 神经系统下达的指令被转化为具体的"动作"——即节点的实际触发、暂停、跳过、并行/串行调度，是连接"决策"与"结构"之间的执行动力层。 |

### 5.1 架构分层示意

```
┌─────────────────────────────────────────────┐
│  前端表现层：无限画布 Web UI（类 Miro）        │
│  节点拖拽 / 连线编辑 / 实时预览 / 调试面板      │
└───────────────────┬───────────────────────────┘
                     │ 画布配置（DAG/StateGraph 定义）
┌───────────────────▼───────────────────────────┐
│  神经系统层：编排引擎（LangGraph 风格状态机）    │
│  状态感知・条件决策・异常与重试策略・循环控制    │
└───────────────────┬───────────────────────────┘
                     │ 调度指令
┌───────────────────▼───────────────────────────┐
│  肌肉层：控制流执行器（Control Flow Executor）  │
│  节点触发・并发调度・暂停恢复・限流退避          │
└───────────────────┬───────────────────────────┘
                     │ 驱动
┌───────────────────▼───────────────────────────┐
│  骨骼层：节点运行时（Node Runtime，骨骼各单元） │
│  采集适配器节点 / 转换节点 / 路由节点 / 输出节点 │
└───────────────────┬───────────────────────────┘
                     │ 生成/消费
┌───────────────────▼───────────────────────────┐
│  血液层：标准化数据流总线（NJSON Data Bus）      │
│  在节点间沿"血管"（连线）持续搬运标准化 JSON     │
└───────────────────┬───────────────────────────┘
                     │ 采集
┌───────────────────▼───────────────────────────┐
│  外部环境层：Playwright 浏览器自动化采集层       │
│  面向无 API 平台的 DOM 抓取・标准化转换          │
└─────────────────────────────────────────────┘
```

### 5.2 设计原则

1. **数据流与控制流解耦**：数据流的"血液"具备一定的自主流转特性（如数据在连线上可被缓存、限速、重放），不必每一次流转都经过神经系统层的显式决策，从而降低编排引擎的心智负担与耦合度。
2. **神经系统只做决策，不做体力劳动**：编排引擎（LangGraph 层）只负责状态判断与路径选择，实际的节点执行与并发调度下放给控制流（肌肉）层，符合职责单一原则。
3. **骨骼可插拔**：节点作为最小单元，支持插件化扩展，新增一种平台适配器或处理逻辑不影响其他层。
4. **足够底层，足够智能**：底层指 Runtime 直接操作浏览器渲染层（DOM/网络层），不依赖平台方 API；智能指编排引擎具备基于 LLM/规则的语义级决策能力（如自动识别页面结构变化并提示用户调整选择器）。

## 6. 機能要件

### 6.1 機能一覧

| 機能ID | 機能名 | 概要 | 優先度 |
|---|---|---|---|

| F-02 | 采集适配器（双模式：API + Playwright） | API 连接器优先、无 API 时回退浏览器自动化，统一接入 IM/项目管理/CRM/MES/ERP 等平台 | 必須 |

| F-04 | 数据流引擎（血液层） | 管理节点间数据包的流转、缓存、限速、重放 | 必須 |
| F-05 | 编排引擎（神经系统层） | 基于状态图实现条件分支、循环、异常处理 | 必須 |
| F-06 | 控制流执行器（肌肉层） | 节点触发调度、并发控制、暂停恢复 | 必須 |
| F-07 | 节点库与插件市场 | 内置常用节点，支持第三方/自定义节点导入 | 必須 |
| F-08 | 可视化调试 | 查看每个节点的输入/输出快照、执行日志、耗时 | 必須 |
| F-09 | 免安装分发 | 前端网页化访问，Runtime 单文件/容器化启动 | 必須 |
| F-10 | 版本管理与回滚 | 画布配置的版本快照、比对、回滚 | 推奨 |
| F-11 | 权限与多人协作 | 多用户同时编辑同一画布、权限分级 | 推奨 |
| F-12 | 平台适配器自愈提示 | 目标平台页面结构变化时自动检测并提示用户调整选择器 | 推奨 |

| F-14 | 数据导出与二次分发 | 将标准化数据导出至数据库、文件、Webhook 等 | 必須 |

### 6.2 機能詳細

#### F-01 无限画布编辑器
- F-01-01 画布支持鼠标滚轮/触控板缩放，范围建议 10%〜1000%。
- F-01-02 支持框选、多选、批量移动、批量删除节点。
- F-01-03 支持节点间连线的拖拽创建、删除、重新连接。
- F-01-04 连线需可视化区分"数据流连线（血管，实线，随数据流动有流光动效）"与"控制流连线（神经/肌肉信号，虚线或箭头样式）"。
- F-01-05 支持画布内文本注释、分组框（Frame）、颜色标记。
- F-01-06 支持撤销/重做（Undo/Redo），至少保留最近 50 步操作历史。

#### F-02 采集适配器（双模式：API + Playwright）
- F-02-00 每个平台适配器需支持"API 模式"与"浏览器自动化模式"的双实现，运行时按平台能力自动选择，或由用户手动指定优先级；两种模式产出的数据经同一套标准化转换逻辑（F-03）统一为 NJSON，保证下游节点无感知差异。
- F-02-01 支持通过可视化方式在目标网页上"点选元素"生成 CSS/XPath 选择器，无需手写代码（用于无 API 场景，含 IM 网页版/客户端内嵌页面、CRM/MES/ERP 私有化系统等）。
- F-02-02 支持登录态保持（Cookie/Session/OAuth Token 持久化），避免每次执行重新登录或重新授权。
- F-02-03 支持分页/滚动加载/无限滚动页面的自动翻页采集。
- F-02-04 支持采集频率限流与随机延时，降低被目标平台风控识别的概率（合规范围内的正常访问节奏模拟）。
- F-02-05 针对 IM 类平台（飞书/企业微信/WeChat/LINE/WhatsApp/Telegram/Slack/Teams/邮件等），需支持消息的收发双向能力：读取新消息、发送消息/回复、读取会话与联系人列表，并统一转换为标准化 JSON 的消息实体（发送方、接收方、时间、正文、附件引用等）。
- F-02-06 采集适配器需在**授权合法使用**前提下运行，系统应在文档与界面中明确提示用户遵守目标平台服务条款及所在地法律法规，不得用于绕过访问控制、爬取受版权/隐私保护的非公开数据。

#### F-03 标准化 JSON 转换
- F-03-01 定义统一的 NJSON Schema（详见第 8 章数据要件），包含：`source`（来源平台标识）、`captured_at`（采集时间）、`schema_version`、`payload`（业务数据体）、`raw_ref`（原始快照引用，可选）。
- F-03-02 提供可视化字段映射工具，将平台原始字段拖拽映射至标准化字段。
- F-03-03 支持自定义转换函数（表达式/脚本片段）处理字段清洗、类型转换。

#### F-04 数据流引擎（血液层）
- F-04-01 数据包在节点间以标准化 JSON 为最小传输单元。
- F-04-02 连线（血管）应支持背压（Backpressure）机制，防止下游节点处理不过来导致内存溢出。
- F-04-03 支持数据在连线上的临时缓存（"血液暂存"），当下游节点暂停时数据不丢失。
- F-04-04 支持数据流量监控（吞吐量、延迟、堆积量）的可视化展示。

#### F-05 编排引擎（神经系统层）
- F-05-01 基于状态图（StateGraph）模型，支持条件分支节点（if/switch）、循环节点、汇聚节点（join/merge）。
- F-05-02 支持异常捕获节点，异常发生时可路由至专门的异常处理分支。
- F-05-03 支持重试策略配置（重试次数、退避算法）。
- F-05-04 支持基于 LLM 的语义决策节点（可选接入大模型对数据内容做语义判断后决定分支走向）。

#### F-06 控制流执行器（肌肉层）
- F-06-01 支持节点级并发度配置（串行/并行/限流并行）。
- F-06-02 支持整体流程的暂停、恢复、终止。
- F-06-03 支持单节点的手动触发（用于调试）。

#### F-07 节点库与插件市场
- F-07-01 内置节点分类：采集类、转换类、路由/条件类、输出类、人工介入类。
- F-07-02 提供插件 SDK（Rust 或 WASM 插件接口），第三方可开发自定义节点。
- F-07-03 插件需声明输入/输出 schema，供画布做连线合法性校验。

#### F-08 可视化调试
- F-08-01 每个节点执行后保留最近 N 次（默认 20 次，可配置）的输入/输出快照。
- F-08-02 支持在画布上直接查看某次执行的数据快照 JSON 树形展示。
- F-08-03 提供执行日志时间轴视图，标注每个节点的开始/结束时间、耗时、状态（成功/失败/跳过）。

#### F-09 免安装分发
- F-09-01 前端以标准网页形式提供，用户通过浏览器直接访问，无需安装客户端。
- F-09-02 Runtime 以单一可执行文件（或最小化容器镜像）形式分发，支持本地一键启动（双击/单条命令），不依赖系统级安装程序、不写入系统注册表（Windows）或需要 root 权限。
- F-09-03 首次启动自动完成本地端口分配、浏览器自动化驱动（Playwright 依赖的浏览器内核）的按需下载与缓存。

#### F-13 定时/事件触发
- F-13-01 支持 cron 表达式定时触发整个画布或指定入口节点。
- F-13-02 支持基于 Webhook 的外部事件触发。

#### F-14 数据导出与二次分发
- F-14-01 内置输出节点：写入本地文件（JSON/CSV）、写入数据库（SQLite/PostgreSQL/MySQL）、HTTP Webhook 推送、写回目标平台（若目标平台支持表单提交类操作，含 IM 消息发送、Jira 工单创建等）。

#### F-15 API 连接器管理
- F-15-01 提供统一的鉴权配置界面，支持 OAuth2、API Key、Webhook 签名校验等主流鉴权方式，覆盖飞书开放平台、Slack、Microsoft Teams、Jira、Miro 等已开放 API 的平台。
- F-15-02 提供统一的限流/退避策略配置，适配各平台 API 速率限制差异。
- F-15-03 支持增量同步（基于游标/时间戳/Webhook 事件），避免全量拉取造成的资源浪费。
- F-15-04 API 凭证与无 API 场景的登录凭证共用第 7.5 节安全要件所定义的加密存储机制。

#### F-16 通用 CRM／企业系统适配框架
- F-16-01 面向"高度可自定义"的 CRM 及 MES/ERP 系统，提供无代码方式配置：自定义 REST/SOAP 端点、自定义数据库连接（含常见工业数据库/中间表）、自定义字段映射规则。
- F-16-02 支持将该类系统的数据模型（如工单、物料、订单、客户）映射为标准化 JSON 的通用实体 schema，便于与 IM/项目管理类数据在同一画布内联动（如 MES 产线异常自动通过飞书/企业微信告警）。
- F-16-03 该框架产出的连接器配置可保存为可复用模板，便于同类系统（如同一 CRM 产品的不同客户部署）快速复制接入。

## 7. 非機能要件

依据 IPA《非機能要求グレード》六大分类整理。

### 7.1 可用性（Availability）

| 項目 | 要求水準 |
|---|---|
| 系统运行持续性 | 单机本地运行场景下，Runtime 应支持长时间（≥7×24 小时）稳定运行不发生内存泄漏导致的崩溃。 |
| 故障恢复 | Runtime 意外退出后重启，应能基于最近一次持久化状态自动恢复未完成的画布执行（断点续传）。 |
| 数据丢失防护 | 画布配置与执行状态需定期自动持久化（默认间隔可配置，建议 ≤30 秒或每次关键状态变更时）。 |

### 7.2 性能・拡張性（Performance & Scalability）

| 項目 | 要求水準 |
|---|---|
| 画布节点规模 | 单画布应支持至少 1,000 个节点、5,000 条连线的流畅渲染与编辑（前端帧率不低于 30fps）。 |
| 数据吞吐 | 单节点数据处理吞吐应达到每秒至少 100 条标准化 JSON 记录（不含浏览器采集类节点，采集类节点受目标平台限制）。 |
| 采集并发 | 支持多个 Playwright 浏览器实例并发运行，具体并发数依据本地硬件资源动态调整并可手动限制，防止资源耗尽。 |
| 水平扩展 | Runtime 架构应预留分布式部署能力（未来可将采集适配器节点调度至多台机器执行），本期作为架构预留项，非本期必须实现功能。 |

### 7.3 運用・保守性（Operability & Maintainability）

| 項目 | 要求水準 |
|---|---|
| 日志 | 提供结构化日志（JSON Lines 格式），支持按节点/画布/时间过滤。 |
| 监控 | 提供本地监控面板，展示 CPU/内存/网络占用及各节点执行状态。 |
| 配置管理 | 画布配置以可导出/导入的文本格式（JSON/YAML）存储，便于版本控制（Git 友好）。 |
| 插件热更新 | 节点插件更新后无需重启整个 Runtime 即可生效（本期为推奨项，非必須）。 |
| 易调整性 | 用户应能在不理解底层实现的前提下，通过画布拖拽/参数面板完成 80% 以上的常见调整需求，无需编写代码。 |

### 7.4 移行性（Portability / Migration）

| 項目 | 要求水準 |
|---|---|
| 跨操作系统 | Runtime 需支持 Windows、macOS、Linux 三大主流桌面操作系统。 |
| 配置可移植 | 画布配置文件应可在不同机器间直接复制迁移并正常运行（不依赖机器绑定的硬编码路径）。 |
| 版本兼容 | 标准化 JSON Schema 需具备版本号（`schema_version`），保证向后兼容，旧版本数据可被新版本 Runtime 正确解析。 |

### 7.5 セキュリティ（Security）

| 項目 | 要求水準 |
|---|---|
| 凭证存储 | 目标平台的登录凭证（Cookie/密码等）需加密存储于本地，不得明文落盘。 |
| 传输安全 | 前端网页与本地 Runtime 之间、Runtime 与外部输出目标之间的通信应支持 HTTPS/WSS。 |
| 权限隔离 | 多人协作场景下，画布的编辑权限、执行权限、凭证查看权限需分级控制。 |
| 合规声明 | 系统需在采集类节点配置界面显著提示：用户需自行确保采集行为符合目标网站服务条款、Robots 协议及所在司法辖区的数据保护法规（如个人信息保护法、著作权法等），系统不承担用户滥用导致的法律责任。 |
| 敏感数据脱敏 | 标准化转换环节应提供可选的敏感字段脱敏（掩码/哈希）能力。 |

### 7.6 システム環境・エコロジー（System Environment）

| 項目 | 要求水準 |
|---|---|
| 运行环境 | 本地个人电脑（4 核 CPU / 8GB 内存起）即可运行基本功能；浏览器自动化采集功能建议 16GB 内存以支持多实例并发。 |
| 依赖最小化 | 除浏览器内核（按需下载）外，不应引入需要用户手动安装的外部依赖（如 JVM、.NET Runtime 等）。 |
| 资源占用可控 | Runtime 空闲状态下 CPU 占用应低于 5%，内存占用应低于 300MB（不含已加载的浏览器实例）。 |

## 8. データ要件

### 8.1 标准化 JSON（NJSON）Schema 定义（草案）

```json
{
  "schema_version": "1.0",
  "source": {
    "platform": "string，平台标识，如 xiaohongshu / twitter / custom",
    "adapter_id": "string，采集适配器唯一标识",
    "url": "string，采集来源页面 URL"
  },
  "captured_at": "string，ISO-8601 时间戳",
  "payload": {
    "id": "string，业务实体唯一标识（若平台提供）",
    "type": "string，数据类型，如 post/comment/profile/order 等",
    "fields": "object，标准化后的业务字段键值对"
  },
  "raw_ref": "string，可选，原始 HTML/截图快照的存储引用路径",
  "trace_id": "string，本次画布执行的追踪 ID，便于调试关联"
}
```

### 8.2 数据流转生命周期

采集（Playwright DOM） → 标准化转换（F-03） → 数据流引擎入血管（F-04） → 编排引擎决策（F-05） → 控制流调度执行下游节点（F-06） → 输出/二次分发（F-14）

### 8.3 数据保留策略

- 原始快照（`raw_ref`）默认保留 7 天，可配置。
- 节点执行快照（调试用）默认保留最近 20 次，可配置。
- 用户可配置数据在流转完成后是否落盘持久化，或仅作瞬时内存流转（默认瞬时，不落盘，降低隐私风险）。

## 10. 制約事項・前提条件

### 10.1 制約事項

1. 对于采取了严格反爬虫、反自动化检测机制的平台，本系统无法保证 100% 稳定采集成功，需依赖用户配置合理的采集策略（限流、指纹伪装等）并接受一定的失败率。
2. 本系统不承诺突破任何平台的登录验证码（CAPTCHA）等人机验证机制，此类场景需人工介入配合。
3. Playwright 依赖的浏览器内核体积较大（通常 100〜300MB／浏览器），首次启动需要下载，需考虑离线场景的预置分发方案。

### 10.2 前提条件

1. 用户已具备对目标平台数据的合法采集与使用权限（如平台服务条款允许、或数据为用户自有账号下的数据）。
2. 运行环境具备可访问互联网的网络条件（用于访问目标平台及依赖下载）。
3. 用户对无限画布式的可视化编排范式有基本理解（或可通过内置引导教程学习）。

## 11. リスクと対応方針

| リスクID | リスク内容 | 影响度 | 対応方針 |
|---|---|---|---|
| R-01 | 目标平台页面结构变更导致选择器失效 | 高 | 实现 F-12 自愈提示机制；提供选择器健壮性建议（优先语义化属性而非纯位置选择器）。 |
| R-02 | 平台反爬策略升级导致采集被封禁 | 高 | 限流、随机化访问节奏、明确合规使用边界、提供风险提示。 |
| R-03 | 无限画布节点规模过大导致前端卡顿 | 中 | 引入虚拟化渲染（视口裁剪）、分组折叠、性能预警。 |
| R-04 | 用户凭证泄露 | 高 | 本地加密存储、避免凭证经过第三方服务器中转。 |
| R-05 | 法律合规风险（数据抓取相关法规） | 高 | 产品层面明确免责声明与合规指引，非技术手段可完全消除，需用户自担合规责任。 |

## 12. 受入基準（検収条件）

1. 能够在无官方 API 的示例平台上，通过可视化点选方式在 10 分钟内配置完成一个采集节点，并成功采集并标准化至少 1 条数据。
2. 画布可完成"采集 → 转换 → 条件路由 → 输出至本地文件"的端到端流程搭建与执行，全程无需编写代码。
3. Runtime 在三大操作系统（Windows/macOS/Linux）上均可实现免安装启动（单命令或单文件双击）。
4. 单画布 1,000 节点规模下，前端交互（拖拽/缩放/连线）保持流畅（不低于 30fps）。
5. 编排引擎能正确执行条件分支、循环、异常重试三类基础控制逻辑的测试用例。
6. 系统在采集节点配置界面明确展示合规使用提示文案。
