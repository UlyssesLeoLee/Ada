## §1 背景 / 問題

QA 登録簿 §5.2 UN-P1-01: **QA-A01 / A02 モジュール境界整理**、期限: **M-01 着手 -3 日**、Owner: **アーキ**。

[`docs/architecture/04-atomic-deployment.md`](../../../architecture/04-atomic-deployment.md) で 16 crate の責務分割を定義したが、具体的な **API 境界（公開トレイト・所有権）** が未整理。`A01 = crate 内部 API 境界`, `A02 = crate 間 API 境界`。

## §2 决策

**採用案**: **トレイトベース境界 + Cargo Workspace 依存方向制約**

- 各 crate の公開 API は `pub trait` で抽象化
- 下位 crate → 上位 crate の依存のみ許可（逆方向禁止、CI で検証）
- 全 crate に `lib.rs` で再エクスポート集約

## §3 選択肢と評価

### Option A: トレイトベース境界 + 依存方向制約 ⭐ 推奨

- **优点**: テスタビリティ向上、モック注入可能、コンパイル時依存検証
- **缺点**: トレイト設計の学習コスト、初版は抽象化しすぎリスク
- **リスク**: 過剰抽象化 → 実装フェーズで剥がす必要
- **可逆性**: 高（トレイト → 具象書き換えは局所的）

### Option B: 直接 struct 公開（具象型）

- **优点**: シンプル、低オーバーヘッド
- **缺点**: テスト時にモック困難、変更影響大
- **リスク**: 内部実装変更 = 外部 API 破壊
- **可逆性**: 中

### Option C: WASM 境界で隔離

- **优点**: 物理的隔離、強制的な抽象
- **缺点**: 性能オーバーヘッド、複雑なビルド
- **リスク**: 開発速度低下
- **可逆性**: 低

## §5 期限 / 触发条件

- **决策期限**: M-01 着手 -3 日（2026-09-12 目標）
- **反映先**:
  - `docs/architecture/04-atomic-deployment.md` §4
  - 各 crate `lib.rs` の再エクスポート整備
  - `tools/check-deps.sh` (依存方向 lint)
- **再评估触发**:
  - トレイト過剰で生産性低下 → 具象公開へ
  - crate 間循環依存 → Cargo features で見直し

## §6 影响範囲 / リスク

- **影响模块**: 全 16 crate の API 境界
- **リスク评估**:
  - トレイト設計の属人化: レビュー必須
  - 過剰抽象化: 実装速度低下
  - 依存方向違反: CI で自動検出
- **緩和策**:
  - アーキ + テックリード合議で全 crate の公開 API レビュー
  - CI で `cargo metadata` + 依存方向 lint
  - 6 ヶ月後レトロスペクティブ
