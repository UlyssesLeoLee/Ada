## §1 背景 / 問題

[`docs/modules/M-10-tenant-middleware.md` §4](../../../modules/M-10-tenant-middleware.md) で `canvas.current_version_id` → `canvas_version.id` のような**自己参照 FK** が含まれる場合、**循環参照が発生**し INSERT 時に FK 違反となる。

QA 登録簿 §5.1 UN-P0-03 期限: **実装着手 -3 日**、Owner: **DBA**。

PostgreSQL の標準機能 DEFERRABLE で同トランザクション内 INSERT/UPDATE を可能にする。

## §2 决策

**採用案**: **Option A (DEFERRABLE INITIALLY DEFERRED)**

```sql
ALTER TABLE canvas
  ADD CONSTRAINT fk_canvas_current_version
  FOREIGN KEY (current_version_id)
  REFERENCES canvas_version(id)
  DEFERRABLE INITIALLY DEFERRED;
```

## §3 選択肢と評価

### Option A: DEFERRABLE INITIALLY DEFERRED ⭐ 推奨

- **优点**: PostgreSQL 標準サポート、INSERT/UPDATE 同トランザクション内 OK、ライブラリ変更不要
- **缺点**: トランザクション外での利用不可（アプリ層でトランザクション境界管理必須）
- **リスク**: トランザクション境界を誤ると FK 違反が実行時に伝播
- **可逆性**: 高（ALTER で変更可能）

### Option B: NULL 許容 + トリガ

- **优点**: 親なし → トリガで更新（柔軟）
- **缺点**: ロジックがトリガに隠れ、テスト困難、デバッグ複雑
- **リスク**: トリガのデッドロック、順序依存
- **可逆性**: 中（トリガ削除＋アプリ層移行必要）

### Option C: 別テーブル化

- **优点**: FK 単純化、NULL 許容問題解消
- **缺点**: 性能影響大（JOIN 増加）、テーブル数増
- **リスク**: クエリ書き換えコスト高、互換性破壊
- **可逆性**: 低（スキーマ変更大規模）

## §6 影响範囲 / リスク

- **影响模块**:
  - `canvas`, `canvas_version` テーブル
  - `crates/ada-tenant-middleware/src/` のキャンバス操作コード
  - 全トランザクション境界（PL/pgSQL 含む）
- **リスク评估**:
  - アプリ層トランザクション境界管理ミス: 全 FK 違反の実行時検出
  - 性能影響: DEFERRABLE で INSERT 時にチェック遅延、ほぼ影響なし
  - テスト: 既存 FK テストを全トランザクション境界で再実行
- **緩和策**:
  - PL/pgSQL 関数で必ずトランザクション明示
  - 単体テストで FK 違反 → 例外ハンドリング確認
  - 月次で FK 整合性監査
