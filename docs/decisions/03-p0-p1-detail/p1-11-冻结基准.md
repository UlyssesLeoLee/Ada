## §1 背景 / 問題

QA 登録簿 §5.2 UN-P1-11: **QA-M01 / M02 凍結基準 + NJSON バージョンポリシー**、期限: **M-01 着手 -3 日**、Owner: **テックリード + アーキ**。

[`docs/architecture/04-atomic-deployment.md`](../../../architecture/04-atomic-deployment.md) の M-01 (acquisition-adapter) で API 凍結基準（いつ API をフリーズするか）と NJSON (JSONB カラム) のバージョンポリシーが未定義。

## §2 决策

**採用案**: **M01 = API SemVer + NJSON = $schema バージョン + deprecation 6 ヶ月**

- **API 凍結基準**: SemVer 2.0 厳格適用
  - Major: 破壊変更 (= API フリーズ解除)
  - Minor: 機能追加（後方互換）
  - Patch: バグ修正
- **NJSON バージョンポリシー**:
  - `$schema` フィールド必須
  - 破壊変更: 新スキーマ `$id` 発行、旧は read-only で 6 ヶ月
  - 双方向 codec: 旧→新、新→旧両方向サポート
- **フリーズ期間**: 機能フリーズは v1.0 後 6 ヶ月維持

## §3 選択肢と評価

### Option A: SemVer 厳格 + $schema バージョン + 6 ヶ月 deprecation ⭐ 推奨

- **优点**: 業界標準、移行期間明示、双方向 codec で相互運用
- **缺点**: バージョン管理コスト、codec テスト増
- **リスク**: deprecation 期間中の保守負荷
- **可逆性**: 高

### Option B: 自由形式（バージョン管理なし）

- **优点**: シンプル
- **缺点**: 破壊変更検出不能、後方互換性破綻
- **リスク**: クライアント障害多発
- **可逆性**: 低

### Option C: Major version = DB カラム追加

- **优点**: 物理的に分離
- **缺点**: DB 肥大、運用複雑
- **リスク**: カラム数増で性能劣化
- **可逆性**: 中

### Option D: 自動 codec（Protobuf / FlatBuffers）

- **优点**: 自動化
- **缺点**: JSON 親和性低、人手編集困難
- **リスク**: 人間可読性喪失
- **可逆性**: 中
