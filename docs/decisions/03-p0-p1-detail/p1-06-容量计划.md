## §1 背景 / 問題

QA 登録簿 §5.2 UN-P1-06: **QA-P06/P07 容量計画**、期限: **プレプロダクション環境構築前**、Owner: **SRE**。

[`docs/requirements/05-nfr-non-functional-requirements.md`](../../../requirements/05-nfr-non-functional-requirements.md) で性能目標 (P06 = キャンバス数、P07 = 同時接続数) があるが、具体的リソースサイジングが未確定。

## §2 决策

**採用案**: **3 段階スケール + Prometheus 自動アラート + 半年毎見直し**

- **小** (1-100 テナント): 1 master, 2 worker, RDS db.t3.medium
- **中** (100-1000): 3 master, 6 worker, RDS db.r5.large
- **大** (1000+): 10 master, 30 worker, RDS db.r5.xlarge + Redis cluster
- アラート: CPU 70%, メモリ 80%, DB 接続 80%, p99 レイテンシ > 1s

## §3 選択肢と評価

### Option A: 3 段階スケール + Prometheus 自動アラート ⭐ 推奨

- **优点**: 段階的コスト最適化、実績ベース計画
- **缺点**: 段階遷移タイミング判断
- **リスク**: スパイク時リソース不足
- **可逆性**: 高

### Option B: 最初から大規模サイジング

- **优点**: 余裕度大
- **缺点**: 初期コスト膨大、利用率低
- **リスク**: 投資回収不能
- **可逆性**: 中

### Option C: サーバレス（Lambda + Aurora Serverless）

- **优点**: 自動スケール、idle コスト 0
- **缺点**: コールドスタート、PostgreSQL 互換制約
- **リスク**: ベンダ依存
- **可逆性**: 中

### Option D: 固定スペック（サイジング変更なし）

- **优点**: 計画簡単
- **缺点**: スケール時の機会損失
- **リスク**: 事業成長の天井
- **可逆性**: 低
